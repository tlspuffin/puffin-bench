### Scheduler hang of 2026-10-06 17:18 — FIXED d10bbeb, deployed

A VulnA group A task (1791299933337) froze the scheduler: the schedule loop spun at 100% of a core in
`Local::EstimatedStepsStartTime` (gdb by the maintainer: ScheduleLoop > SearchTasksToRun > EstimatedStepsStartTime >
DurationHistory::Estimate) holding the schedule lock; /api/health "busy" (the new light caught it), state file stale.
Cause: advancing the simulated time only freed the cores ending exactly then; a step could never fit, next end =
"infinite", endless loop. Fix: free every core busy until the new time, stop when no core gets free later, an
iteration cap with a log line. Reproduced with throwaway instances (39 cores, cassis duration history, the group A
flow with sleeping steps): deployed binary busy after 3 s and its stop needed SIGKILL; fixed one up, 78/78 steps
estimated, stop 6 s. Very likely also the cause of the silent 90 s stops of the morning (a loop that never sees the
stop request). The stop of 17:35 needed SIGKILL; task 1791299933337 (Lucca, VulnA 5c588a, started 17:18) was lost:
the maintainer may relaunch it.

15. ASAN analysis (done, verified in the tlspuffin sources; to implement in the launcher):
    - Since tlspuffin 854dbaa11 (2024-10-03, "build: dynamically register the PUT instrumentation"): with a vendor
      preset (C harness, `cputs`), the preset's `asan = true` (presets.toml) builds the library with
      `-fsanitize=address` (`puffin-build/vendors/*/builder.cmake`) and `puffin-build/src/harness/put.rs` adds
      the link args (`-fsanitize=address -shared-libasan`, runtime rpath) from the library metadata. The C harness
      glue is not compiled with ASAN (only sancov/claimer flags), the Rust code neither (`-Z sanitizer` is
      commented out in `.cargo/config.toml`). The `asan` cargo feature
      (`tlspuffin/Cargo.toml: asan = ["openssl-src?/asan", "wolfssl-sys?/asan", "boringssl-sys?/asan"]`) only acts
      on the in-tree Rust-harness crates, which a vendor build does not enable: no effect there.
    - **Before 854dbaa11** (all the 2023–Sept 2024 history the bench runs): `tlspuffin/build.rs` adds the ASAN
      link args only `if cfg!(feature = "asan")`. A `-asan` vendor library without the feature lacks the ASAN
      runtime link (link failure or a binary without the runtime). So the feature IS required there.
    - Rust-harness builds (library chosen by a feature, e.g. `wolfssl540`): the `asan` feature selects the ASAN
      build of the in-tree library (`-asan` suffix in `crates/*-src`, `asan` option in `crates/*-sys/build.rs`).
    - Environment: `.cargo/config.toml` `[env] ASAN_OPTIONS = "verify_asan_link_order=1:detect_leaks=0:abort_on_error=1"`
      only applies through `cargo run`; direct runs (replays) must set it themselves (done: `.currentlaunch` records
      `LAUNCH_ASAN_OPTIONS`, `AsanOptions` in objectives_live.sh).
    - In the bench: the job configs already pair every `-asan` preset with the `asan` feature
      (`PR_perf_cargo.json`; compat rule `libressl_asan` adds it for LibreSSL). Side effects of the feature in our
      scripts: `PR_common.sh` disables faketime when the features contain `asan` (lines ~245, ~293) but not for an
      `-asan` preset alone; `DetectAsan` checks the binary (`__asan_report_*` symbols, runtime) and records
      `asan.instrumented`, shown as ASAN✓/✗ on Results.
    - Launcher rule: when the preset ends in `-asan`, add the `asan` feature by default (needed before 2024-10-03,
      harmless after) and warn if the user removes it; warn when the `asan` feature is set with a non-asan preset
      (old commits would link the ASAN runtime against a non-instrumented library); Rust harness: `asan` default on.

## 6. How to test

Web files against the live services without touching the install: `overlayproxy.py <port> <upstream> <dir>
<url prefix>` (scratch tool: serves the files of <dir> under the prefix, forwards the rest), e.g. port 18083 in front
of 10083 with the changed publisher files — never the template `summary_config.js` (the deployed one is
generated). Live objectives: run objectives_live.sh with `PB_ROOT=<scratch root>` (runs/<task> symlinked to the
real folder) and `PB_SCHEDULER_API=<mock answering /api/task/<id>/state>`; final reports:
`PB_ROOT=<scratch root>` with the export json/zip symlinked under data/exports.

Throwaway scheduler instances on cassis (used for item 1): a fresh root under the scratch folder with its own
config.json (port 18082/18092, `nbCores` 1 and `excludeCores` 1..39 = core 0 only, cgroup root
`/sys/fs/cgroup/user.slice/pb-test-none` = cgroups off and no user.slice update, publisher on a dead port), a fake
`sudo` first in PATH, `--only-install --force-install` then the binary under `taskset -c 0 nice -n 19`. The
deployed binary `/srv/puffin-bench/bin/scheduler` can be run the same way for A/B comparisons. Kill only the
test's processes (match their cwd under the test root: production runs as the same user).

On cassis (read-only diagnostics are allowed): task folders `/srv/puffin-bench/data/runs/<task>/` (step folders
`executor/<step>-<rank>-<attempt>/`, `.currentlaunch`, `experiments/*/objective/`), exports
`/srv/puffin-bench/data/exports/<task>.{json,zip}` (and `Canceled/`), objectives pages and state
`/srv/puffin-bench/data/html/objectives/`, scheduler state `curl -s http://127.0.0.1:10082/api/tasks/running`,
task state `/api/task/<id>/state`, users DB via `/api/users`. Manual replays: source the step's `.currentlaunch`
and run `${LAUNCH_PREFIX} ${LAUNCH_BINARY} ${LAUNCH_FLAGS} execute <trace>` with `RUST_LOG=debug` and
`ASAN_OPTIONS=${LAUNCH_ASAN_OPTIONS}` in a scratch folder — on core 0 only (`taskset -c 0 nice -n 19`), never on
the fuzzing cores. A local scheduler for UI tests can run on another port (e.g. 18082) from the separate clone's
build, with its own data folder.

Without the test machine:

- Build the scheduler: `cmake -S scheduler -B <build dir> && cmake --build <build dir> --target scheduler -j8`.
  Run a local instance: a `config.json` with port 18082 and local paths (copy `scheduler/samples/scheduler/config.json`,
  change port/paths), `./scheduler --only-install --force-install config.json`, then `./scheduler config.json`;
  submit tasks with `curl -F config=@flow.json -F script=@steps.sh -F name=… -F user=… -F job_type=…
  http://localhost:18082/api/task/new` (see `tlspuffin/scripts/test_machine/dummy_tasks.sh`).
- Commit descriptions need git_restapi: a small mock answering `/api/git/history/tlspuffin` and
  `POST /api/git/logs/tlspuffin` on port 18081 is enough.
- Results pages: serve a copy of `tlspuffin/data/html/{publisher,common}` + `scheduler/html/board/{nav,navhelp,
  hostlinks}.js` (under `html/board/`) + `tlspuffin/data/html/third-party/plotly` with `python3 -m http.server`,
  and a test page that imports `summary_render.js` / `summary_graphoverview.js` with fixture commits and a fake
  metrics object (`GetValuesForType`, `GetValuesForSubType`, `GetValues`, `GetCommits`, `GetCommit`, `HaveCommit`).
- Screenshots and interactions: Playwright with the preinstalled Chromium
  (`import { chromium } from '/opt/node22/lib/node_modules/playwright/index.mjs'`), locale `en-US`
  (an invalid default locale breaks `toLocaleString`).
- JS syntax: `node --check file.js`; C++ files without a full build: `g++ -std=c++20 -fsyntax-only` with the Poco and
  RapidJSON include dirs under `scheduler/third-party/*-install/Release/include`.
