# Scheduler — REST API Reference

All endpoints are served under the prefix `/api/`. Static assets are served under `/files/`. Routing is regex-based, implemented in `src/scheduler/server/request_handler_factory.hxx`; each route maps to a `RequestHandler` subclass (generated by the `REQUESTHANDLER` macro in `src/scheduler/server/request_handler.hxx`) whose implementation lives in `src/scheduler/server/request_handler.cxx`.

Base URL: `http[s]://<host>:<port>/api`

---

## CORS and OPTIONS

Most handlers call `RequestHandler::ManageCORS()` first, which unconditionally sets:

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type
```

and, if the request method is `OPTIONS`, replies `200 OK` with no body and returns.

**Important:** `RequestHandlerFactory::createRequestHandler()` only dispatches on `GET`, `POST`, `PUT`, `PATCH`, `DELETE` — there is no `OPTIONS` branch. An `OPTIONS` request never reaches a handler that would call `ManageCORS()`; it always falls through to `RequestHandlerError`, which returns `404 Path not found: <uri>`. In practice CORS preflight is **not** actually served by any route today, even though every handler that does answer a real request sends the CORS headers above.

`ManageCORS()` is also **not called** by `RequestHandlerTaskNew` (`POST /api/task/new`), `RequestHandlerCachePut`, `RequestHandlerCacheGet`, or `RequestHandlerFiles` — those four handlers never set CORS headers on their responses.

## Task Management

### Submit a Task

```
POST /api/task/new
Content-Type: multipart/form-data
```

**Form fields** (parsed via `Poco::Net::HTMLForm` + a custom `PartsHandler`):

| Field | Kind | Required | Description |
|-------|------|----------|-------------|
| `name` | form field | no (defaults to `""`) | Human-readable task name |
| `config` | file part | yes | Flow JSON file (workflow definition) |
| `script` | file part | yes | Bash script defining step functions |
| `files[]` | file part(s) | no | Additional input files; repeatable, uploaded and made available to steps |
| `args[KEY]` | form field | no | One entry per key; becomes a task-level argument available to all steps |
| `runtime[KEY]` | form field | no | One entry per key; used to resolve `${RUNTIME_KEY}`-style placeholders embedded in the flow JSON (e.g. `"priority": ${RUNTIME_PRIORITY}`) |
| `user` | form field | no (defaults to `"anonymous"`) | Username for task tracking |
| `job_type` | form field | no (defaults to `"unknown"`) | Job category for the user/job-type index |

Duplicate keys inside `args[...]` or `runtime[...]` (i.e. the same key appearing twice) make the request fail with a `500` and an error body.

**Response `200 OK`:**
```json
{ "success": true, "task_id": "1713240000000" }
```
Note `task_id` is emitted as a JSON **string**, not a number.

**Response `200 OK`, application-level failure** (missing `config` or `script` part — status code is *not* changed):
```json
{ "success": false, "error": "Missing config or script file." }
```

**Response `500 Internal Server Error`** — any other failure (invalid flow JSON, duplicate `args[]`/`runtime[]` key, empty key, `ScheduleAPI::AddTask` throwing):
```json
{ "success": false, "error": "<exception message>" }
```

**Example:**
```bash
curl -X POST http://localhost:10082/api/task/new \
  -F "name=my-experiment" \
  -F "config=@./flow.json" \
  -F "script=@./run.sh" \
  -F "args[COMMIT_ID]=abc123" \
  -F "runtime[PRIORITY]=10" \
  -F "user=alice" \
  -F "job_type=perf"
```

### List Running Tasks

```
GET /api/tasks/running
```

Returns the content of `<exportPath>/tasksmanager.json` (see `Schedule::TaskManagerStateFile()`), which is rewritten by `Schedule::SaveStatus()` on every scheduler-loop iteration and on every task/step mutation. The file/response embeds two top-level members: `tasksmanager` (`{"tasks": [...]}`, the array of all in-memory tasks) and `executors` (per-executor stats).

**Response `200 OK`:**
```json
{
  "success": true,
  "data": {
    "tasksmanager": {
      "tasks": [
        {
          "id": 1713240000000,
          "name": "my-experiment",
          "user": "alice",
          "job_type": "perf",
          "request_cancel": false,
          "state": "Running",
          "priority": 0,
          "publish_link": "",
          "flag": {},
          "root_steps": [9876543210],
          "steps": {
            "9876543210": {
              "uuid": 9876543210,
              "step_id": 0,
              "rank_id": 0,
              "attempt_id": 0,
              "name": "build",
              "state": "Done",
              "exit_code": 0,
              "nb_cores": 2,
              "time_points_ms": [1713240000000, 1713240120000],
              "user_run_state": ""
            }
          }
        }
      ]
    },
    "executors": []
  }
}
```

See `docs/monitoring-output-cache.md` and the field table below for the complete set of `Task`/`Step` JSON fields.

**Response `500 Internal Server Error`** — if `<exportPath>/tasksmanager.json` cannot be opened:
```json
{ "success": false, "error": "Server can't read schedule status" }
```

### Get Step Output

```
GET /api/task/<taskID>/<stepUUID>/<stepID>/output/<type>/<size>/<offset>
```

Regex: `/api/task/(\d+)/(\d+)/(\d+-\d+-\d+)/output/(stdout|stderr|[0-9]+)/(\d+)/(-?\d+)`

**Path parameters:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `taskID` | uint64 | Task ID |
| `stepUUID` | uint64 | Step UUID |
| `stepID` | string | Step logical ID, e.g. `"0-0-0"` |
| `type` | `stdout` \| `stderr` \| integer | Which stream to read. An integer selects entry `type` (0-based) from the step's declared `streams` array in the flow JSON, for live-tailing arbitrary files the step writes |
| `size` | uint64 | Maximum bytes to return |
| `offset` | int64 | Byte offset from the start of the retained data |

Resolution order (`Schedule::GetOutput()`):
1. If the task is still in memory (running/pending), the read is served by the executor:
   - `type == "stdout"`/`"stderr"`: reads from the step's in-memory ring buffer (`MemoryRing`, via `FDCaptureThread::Read()`), sets `partial=true`.
   - `type` is numeric: resolved as an index into `Step::readable_files_` (the `streams` array); the file is read live off disk under the task's run directory, with `live=true`, `supportSeek=true`, `partial=true`.
2. Otherwise (task not in memory) and `type` is `stdout`/`stderr`: the first existing archive among `exportPath/<taskID>.zip`, `exportPath/Canceled/<taskID>.zip`, `exportPath/<taskID>.tgz`, `exportPath/Canceled/<taskID>.tgz` is opened, and `logs/<type>.<stepID>.txt` is extracted (`FileCompressed::ExtractFileData`). Numeric `type` is not resolvable for completed tasks.

**Response `200 OK`:**
```json
{
  "success": true,
  "data": "<base64-encoded chunk>",
  "partial": false,
  "size": 4096,
  "filesize": 32768,
  "state": 4,
  "support_seek": true,
  "start_offset": 0,
  "file_start_offset": 0,
  "live": false
}
```

`state` is the numeric `FileReadState` enum value (`Error_Access=0`, `Error_Open=1`, `Error_OverFlow=2`, `NotExecuted=3`, `Ok=4`, `EndOfFile=5`). When a partial/live buffer is served, the handler additionally sends `Cache-Control: no-store, no-cache, must-revalidate` and `Pragma: no-cache`.

**Response `500 Internal Server Error`** — missing parameters, or `state` not in `{Ok, EndOfFile}`:
```json
{ "success": false, "error": "Server can't read requested output" }
```

### Cancel a Task

```
DELETE /api/task/<taskID>
```

Calls `Schedule::CancelTask(taskID, "rest api request")`, which finds the first step belonging to the task, calls `Task::Cancel()` (sets `cancel_source_`, `state_ = Cancelled`, `request_cancel_ = true`), and persists state. The scheduler loop stops dispatching new steps for the task and kills the currently running step on the next iteration.

**Response `200 OK`:**
```json
{ "success": true }
```

**Response `200 OK` on failure** (status code is not changed by the handler in the error path, only internally by the API call before throwing — actual observed body):
```json
{ "success": false, "error": "task cancel failed" }
```

### Cancel a Step

```
DELETE /api/task/<taskID>/step/<stepUUID>
```

Despite the field name, `stepUUID` is not a UUID/GUID string — it's `Step::uuid_`, a plain `uint64_t` assigned from a process-wide `std::atomic<uint64_t>` counter (`Step::next_uuid_`, starting at 0 and incremented per step created, across all tasks). The route regex (`/api/task/(\d+)/step/(\d+)`) matches a decimal integer, e.g. `DELETE /api/task/42/step/9876543210`.

Calls `Schedule::CancelStep(taskID, stepUUID)`, which scans the step list for the matching task/UUID pair and sets `Step::request_cancel_ = true`; if the step is currently running, `KillAndMarkCancel()` terminates it via the executor.

**Response `200 OK`:**
```json
{ "success": true }
```
**Response on failure:** `{ "success": false, "error": "step cancel failed" }`

### Update Task Priority

```
PATCH /api/task/<taskID>/<priority>
```

Regex: `/api/task/(\d+)/(-?\d+)` — this route is **not present in the README's summary table** but is registered and functional. `priority` is a signed integer (`int64_t`); larger values are scheduled sooner. Calls `Schedule::TaskUpdatePriority(taskID, newPriority)`, which sets `Task::priority_` and re-orders the task's steps within the scheduler's internal step list so it stays sorted with higher-priority tasks earlier. No-op (returns success) if the new priority equals the current one.

**Response `200 OK`:**
```json
{ "success": true }
```
**Response `500 Internal Server Error`** if no step for `taskID` was found: `{ "success": false, "error": "step cancel failed" }` (the error message is copy-pasted from the cancel-step path in the current implementation).

### Get Task State

```
GET /api/task/<taskID>/state
```

Calls `Schedule::GetTaskData()`: first tries `GetTaskFinalData()` (task fully archived — both `<id>.json` and `<id>.zip`/`.tgz` present under `exportPath` or `exportPath/Canceled`); if that fails, falls back to serializing the **in-memory** task (`Task::ToJSON()`) directly as a JSON string.

**Response `200 OK`, task still running/pending** (served inline, not as a file):
```json
{ "task": { "id": 1713240000000, "name": "my-experiment", "state": "Running", "...": "..." } }
```

**Response, task already archived:** the raw exported task JSON file is streamed back with `Content-Disposition: attachment; filename="<taskID>.json"` (via `SendFile`, `Content-Type: application/json`).

**Response `400 Bad Request`** — task not found at all: `{ "success": false, "error": "task does not exist" }`

---

### Get Task Final State

```
GET /api/task/<taskID>/final_state
```

Same handler as `GET /api/task/<taskID>/state` but with `final=true`: only returns data if the task is fully archived (`GetTaskFinalData()` succeeds); a task that exists only in memory is treated as **not found**.

**Response `200 OK`:** the exported task JSON file, `Content-Disposition: attachment; filename="<taskID>.json"`.

**Response `400 Bad Request`:** `{ "success": false, "error": "task does not exist" }`

---

### Get Task Artefacts

```
GET /api/task/<taskID>/artefacts
```

Calls `Schedule::GetTaskFinalData()` and streams back the artefacts archive path it resolves (a `.zip`, or `.tgz` for legacy tasks), with `Content-Disposition: attachment; filename="<taskID>-artefacts.<ext>"`.

**Response `400 Bad Request`:** `{ "success": false, "error": "task does not exist" }` or `"task artefact filename invalid"` if the resolved path has no extension.

## User and Job Type Tracking

Backed by `<exportPath>/users.json`, maintained by `UsersAPI` (`src/scheduler/api/users_api.cxx`). Structure on disk: `{"<user>": {"<job_type>": {"<taskID>": {"name", "running", "cancelled", "publish_link", "flag"}}}}`.

### List Users

```
GET /api/users
```

**Response `200 OK`:**
```json
{ "success": true, "data": ["alice", "bob"] }
```

### List Job Types for a User

```
GET /api/user/<username>/job_types
```
Regex for `<username>`: `[a-zA-Z0-9_-]+`.

**Response `200 OK`:**
```json
{ "success": true, "data": ["perf", "vulnerabilities"] }
```
**Response `500 Internal Server Error`** if the user is unknown: `{ "success": false, "error": "step cancel failed" }` (shared, copy-pasted error string).

### List Tasks for a User and Job Type

```
GET /api/user/<username>/<jobType>/tasks
```
Regex for both `<username>` and `<jobType>`: `[a-zA-Z0-9_-]+`.

Entries whose task record is stale (not running, not cancelled, and no matching export/cancel JSON exists on disk) are dropped and the on-disk index is rewritten as a side effect of this call.

**Response `200 OK`:**
```json
{
  "success": true,
  "data": [
    {
      "id": 1713240000000,
      "name": "my-experiment",
      "running": false,
      "cancelled": false,
      "publish_link": "http://publisher.example.com/files/tlspuffin#1713240000000",
      "flag": { "color": "#6f6f00" }
    }
  ]
}
```
`publish_link` is `""` when no publish server is configured for the task. `flag` is `{}` if `Flag()` was never called by the step script.

## Cache

The `<id>` path segment is constrained by the routing regex to `[a-zA-Z0-9_-]+` for both `GET` and `PUT /api/cache/<id>`; the cache implementation itself (`src/scheduler/cache/cache.cxx`) performs no additional ID validation.

### Store a File in Cache

```
PUT /api/cache/<id>
Content-Type: application/json
```

**Body:**
```json
{
  "path": "/absolute/path/to/file",
  "computeMD5": true,
  "force": false
}
```

| Field | Default | Meaning |
|-------|---------|---------|
| `path` | required | Source file path, must exist |
| `computeMD5` | `false` | Accepted and stored on the pending request, but **not currently used** — `Cache`'s background copy thread always records an empty MD5 string; no MD5 is actually computed for cached files in the present implementation (`FileInformations::md5_` stays `""` regardless of this flag) |
| `force` | `false` | Overwrite if `id` already exists |

The copy itself is asynchronous: `Cache::Put()` registers a placeholder entry and returns immediately; a background thread performs the `std::filesystem::copy_file` and flips the entry to "full" once done.

**Response `200 OK`:**
```json
{ "success": true }
```
**Response `500 Internal Server Error`** — missing `id`/`path`, or invalid JSON body: `{ "success": false, "error": "..." }`

### Retrieve a Cached File

```
GET /api/cache/<id>
```

**Response `200 OK`:**
```json
{ "success": true, "state": "Ok", "path": "/cache/storage/abc123" }
```

**`state` values** (`CacheAPI::Get()` maps `Cache::GetStatus` to these exact strings):

| Value | Meaning |
|-------|---------|
| `Ok` | File is available at `path` |
| `Locked` | File is still being copied into the cache |
| `Not Available` | ID unknown to the cache |

Note there is no `md5` field in the response body in the current implementation.

**Response `200 OK`, missing id:** `{ "success": false, "error": "Missing required parameters id." }`
**Response `500 Internal Server Error`** on internal exception: `{ "success": false, "error": "..." }`

## Static Files

```
GET /files/<path>
```

Handled by `RequestHandlerFiles`, mounted for any URI starting with `/files/`. Serves files from `<config.server.html>/<path>` (default `html/`). `/files/` (empty path) serves `index.html`. Requests are canonicalized and checked to stay inside the configured `html` root (rejecting `..` traversal with `400 Bad Request`); a path that does not resolve to an existing file returns `404 Not Found`.

MIME type is derived from the file extension via a small built-in table: `.txt`→`text/text`, `.html`→`text/html`, `.css`→`text/css`, `.json`→`application/json; charset=utf-8`, `.js`→`text/javascript`, `.jpg`/`.jpeg`→`image/jpeg`, `.png`→`image/png`, `.svg`→`image/svg+xml`; anything else is served as `application/octet-stream`.

The dashboard is reachable at `/files/board/board.html` once the embedded board assets have been installed (`./scheduler --force-install` or first run).

## Error Responses

Handlers generally return JSON bodies of the shape:
```json
{ "success": false, "error": "description of what went wrong" }
```
except `RequestHandlerError` (unmatched route), which returns plain text:
```
404 - Path not found: <uri>
```

Observed HTTP status codes:

| Code | Meaning |
|------|---------|
| 200 | Success, or an application-level failure that the handler did not escalate (see per-endpoint notes above) |
| 400 | Bad request — missing task, invalid file path, path traversal attempt on `/files/*` |
| 404 | No route matched the method/URI |
| 500 | Internal server error — invalid JSON body, missing required field, exception during processing |
